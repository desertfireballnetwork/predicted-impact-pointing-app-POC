# Progress Log — Fireball Notification POC

Tracks decisions and milestone status for the Android proof-of-concept. See the approved plan for full detail: `/home/hadry/.claude/plans/shiny-meandering-abelson.md`.

## Goal

Prove on-device feasibility of: simulate a fireball/re-entry event (start/end lat/lon/height + absolute time) → check horizon visibility from GPS location (>1° elevation) → guide the observer with a simple 2D HUD (compass ring + elevation gauge, driven by the phone's rotation-vector sensor) → countdown to event start. Sideload-only install (no Play Store).

## Key decisions

- **2026-08-05**: HUD is a simple 2D compass/elevation dial, not a camera AR overlay — user explicitly rejected the camera-view approach for simplicity.
- **2026-08-05**: Kotlin + Jetpack Compose, single module, no DI/Room/nav-library — kept minimal for POC scope.
- **2026-08-05**: Geometry ported from the DFN codebase's validated formulas in `/opt/RMS-NOC/RMS/Astrometry/Conversions.py` (`latLonAlt2ECEF`, `ECEF2AltAz`) rather than re-derived, to avoid trig sign-error bugs.
- **2026-08-05**: Sky track over time = linear interpolation along the ECEF line between start/end points by elapsed time fraction, converted to az/el each frame. Simplest approach that still sweeps the target across the sky.
- **2026-08-05**: Location via plain `LocationManager`, not Play Services `FusedLocationProviderClient` — one less dependency for a POC.
- **2026-08-05**: Build/install path is command-line Gradle + `adb`/file copy, no Android Studio required. Dev machine had no Android SDK installed at project start (only OpenJDK 21); SDK cmdline-tools installed as milestone M0.

- **2026-08-05**: M6 — added an auto-generated alert feed, requested after the initial plan was already built. New `EventType` (FIREBALL/REENTRY) and `EventGenerator` (`model/EventGenerator.kt`) produce randomized-but-plausible events per type:
  - **FIREBALL**: entry angle 5–85°, visible 100km → 20km, speed 15–30 km/s (typical meteor speed).
  - **REENTRY**: entry angle 0.5–5° (user said "<5°"; floored at 0.5° since tan(angle)→0 makes the ground track blow up toward infinity as angle→0), visible 100km → 50km, speed 7–8 km/s (~orbital decay speed).
  - Ground track distance is derived from `heightDrop / tan(entryAngle)` — this is why shallow re-entries produce long tracks and steep fireballs produce short ones, matching real physics. Event duration is the 3D (ECEF) slant distance divided by a randomized speed in the type's range, not a fixed number — ties the sky-sweep speed to something physically motivated.
  - Start point is placed at a random bearing/distance from the observer's GPS position (falls back to the form's default anchor if no GPS fix yet) using a standard great-circle destination-point formula (spherical-Earth approximation — fine for placing test points, doesn't need WGS84 precision the way the visibility math does).
  - **2026-08-05 correction**: start-point offset cap changed from an initial 1500km to **800km** per explicit user request, to keep generated events within a real chance of clearing the ~1129km geometric horizon distance for a 100km-altitude point. Note this only bounds the *start* point — very shallow re-entry tracks (long ground distance from the angle/tan relationship) can still push the *end* point well beyond the horizon even when the start is close, so a re-entry may visibly start above the horizon and sink below it during the sweep. This is physically realistic (you lose sight of a shallow re-entry as it recedes into the distance), not a bug, but worth knowing if "always visible for a full simulated event" is ever expected.
  - New `AutoFeedScreen` (`ui/AutoFeedScreen.kt`): a `LaunchedEffect` loop generates a new random-type event every `EventGenerator.CYCLE_MS` (2 min), reusing the existing `CountdownScreen`/`HudScreen` composables rather than duplicating their logic. A new event always replaces whatever's currently showing, even mid-countdown or mid-HUD — matches how a real alert feed would interrupt you, and avoids building a queueing system that wasn't asked for. Reachable via a new "Start auto alerts" button on `FormScreen`, alongside the existing manual "Simulate" flow (kept, not replaced).
  - Notifications: `NotificationHelper` (`notify/NotificationHelper.kt`) creates a channel and posts a "look up in 1 minute" notification `EventGenerator.NOTIFY_LEAD_MS` (60s) before each event's start. Fires via a fire-and-forget child coroutine launched inside the generation loop (cancelled automatically if the user leaves the auto-feed screen). Requires `POST_NOTIFICATIONS` (Android 13+/API 33+ only) — added to the manifest and requested at app launch alongside the location permission; on lower API levels no runtime grant is needed. Scoped to "while running" only, per explicit user framing, so this deliberately does **not** use `WorkManager`/`AlarmManager`/a foreground service — it's a plain in-process coroutine timer that stops if the app is killed or backgrounded past the OS's background-execution limits.

- **2026-08-05**: first real device walk-test happened — app installs and runs. Two issues reported and fixed:
  - **Bug: notifications never fired.** Root cause was in `MainActivity`/`AppRoot`: two separate `rememberLauncherForActivityResult(RequestPermission())` launchers were both `.launch()`ed back-to-back in the same `LaunchedEffect` (location, then notifications). Firing a second permission request while the first system dialog is still pending is a well-known Android footgun — the second request gets silently dropped, so `POST_NOTIFICATIONS` was likely never actually granted, and `NotificationHelper.notifyUpcoming` was silently no-op'ing on the permission check. Fixed by switching to a single `ActivityResultContracts.RequestMultiplePermissions()` launcher requesting both permissions in one batched call, which is also the officially recommended pattern for requesting more than one permission at once.
  - **Design change: HUD replaced with a virtual horizon.** The compass-ring + separate elevation-gauge design (M4) wasn't what was wanted. Replaced with `VirtualHorizonHud` (`ui/VirtualHorizonHud.kt`): a simulated camera view (still no actual camera preview) showing a horizon line, the full predicted track overlaid as a line (not just the current point), and an edge arrow pointing toward the event's start point when it's outside the current field of view. `CompassDial.kt` deleted.
    - This needed the phone's **full rotation matrix**, not just azimuth/elevation of the pointing direction, so `OrientationTracker` now emits `DeviceOrientation(pointing: AzEl, rotationMatrix: FloatArray)`. Important correctness detail: `SensorManager` reuses the same `FloatArray` buffer for every sensor event, so the matrix must be `.copyOf()`'d before emitting — otherwise every past `StateFlow` emission would alias the same mutable array and silently corrupt itself on the next sensor tick.
    - The projection math (`geometry/Projection.kt`: `worldToDeviceFrame`, `projectNormalized`, `arrowAngleDeg`) is standard 3D view-space projection — world az/el → device-local XYZ via `deviceVec = R^T * worldVec` (R is orthogonal so its inverse is its transpose), then perspective divide by depth for on-screen points. Deliberately **not** a tangent-plane/az-el-delta approximation with a separate manually-derived roll correction — using the full rotation matrix directly means roll is automatically and correctly accounted for with no extra work, and is actually simpler than the alternative. This was moved out of the `ui` package into `geometry` (pure math, zero Compose/Android dependency) specifically so it could get the same unit-test treatment as the rest of the geometry — given this project has already had two real sign/axis bugs in orientation-related code (the top-edge-vs-camera-axis correction, and this notification bug), that risk pattern justified the extra rigor. 7 new tests in `ProjectionTest.kt`, verified by hand-deriving a known rotation matrix (phone level, facing due north) and checking that north/level projects to screen center, east projects right, an elevated point projects up, points outside the FOV are flagged off-screen, and points behind the device are flagged not-in-front.
    - The off-screen arrow direction (`arrowAngleDeg`) deliberately does **not** reuse the perspective-projected x/y (which blows up / gives nonsense when a point is near or behind the 90°-from-boresight boundary). It uses `atan2(devX, devY)` directly on the un-projected device-frame vector instead, which stays well-behaved for any angle including directly behind.
  - Still outstanding: haven't re-walked-tested this specific round of fixes on the device yet (notification fix + virtual horizon rewrite) — next step is to rebuild, reinstall, and confirm both the notification and the new HUD actually work as intended outdoors.

- **2026-08-05**: M9 — Sun and Moon position markers, self-contained low-precision astronomical algorithms, no external ephemeris service/library/dependency, all in `geometry/CelestialPositions.kt`:
  - **Sun**: standard NOAA/Michalsky-style low-precision formula (mean longitude + equation-of-center correction), accurate to roughly 0.01° — vastly more precise than this app needs.
  - **Moon**: the Moon's orbit is perturbed enough that a bare mean-position formula is off by several degrees, so this uses a truncated Meeus-style periodic series (~12 longitude terms + 8 latitude terms — the dominant corrections only, not the full ~60-term high-precision table), accurate to roughly a few tenths of a degree. Both barely move over the span of one simulated event, so they're computed once at `event.startTimeEpochMs` ("time of impact", per instruction) rather than live every frame.
  - **Az/el conversion reuses existing tested code instead of new spherical trig.** Rather than the classic hour-angle formula (`sin(alt) = sin(dec)sin(lat) + cos(dec)cos(lat)cos(H)` etc. — a well-known source of azimuth-quadrant sign bugs), RA/Dec is converted to a unit vector, rotated from the inertial frame into ECEF by Greenwich Mean Sidereal Time (the standard equinox-based ECI→ECEF rotation used in satellite tracking), placed 1 AU away from the observer along that direction, and run through the same `ecefToAltAz()` already validated in M1. Ignores parallax (negligible for the Sun, up to ~1° for the Moon) — acceptable given the HUD's existing 5° alignment tolerance.
  - 6 new unit tests in `CelestialPositionsTest.kt`, deliberately checking against independently-known astronomical facts rather than just internal consistency: Sun declination ≈ +23.44° at the June solstice, ≈ -23.44° at the December solstice, ≈ 0° at the March equinox; plus meridian-transit geometry checks (object directly overhead when declination equals observer latitude and hour angle is zero; object due north when its declination exceeds the observer's latitude on the meridian). All 6 passed on the first run — unlike several earlier orientation-related pieces of this app, no sign-convention bug needed fixing here.
  - `HudScreen` computes `sunAzEl`/`moonAzEl` once per event (`remember(event, observerState)`), filtered through the existing `isVisible()` (>1° elevation) so they only appear on the HUD when actually above the horizon, matching the ask. `VirtualHorizonHud` draws them as small labeled circles (amber "Sun", pale "Moon") using the same projection pipeline as the track and compass marks — no new rendering path needed.
